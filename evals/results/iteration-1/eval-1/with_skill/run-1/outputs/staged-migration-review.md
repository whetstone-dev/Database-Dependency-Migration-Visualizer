# Staged migration review

This plan is operator review material. No SQL was executed, and the analyzer did not replay the migrations into a target schema.

The source model and [impact paths](resolved-impact-paths.json) identify customer key consumers. Direct consumers include `customers_pkey`, the `addresses.customer_id` and `orders.customer_id` FK relationships, their constraints, `customer_summary`, and both application SQL files. `orders_customer_idx` and the view's three owned columns appear through transitive paths. The view-column ownership paths do not establish separate expression lineage for each output column.

| Phase | Supplied proposal and finding | Required gate | Recovery boundary |
|---|---|---|---|
| Expand | `001_add_customer_uuid.sql:2-4` adds nullable UUID representations to customers, orders and addresses. Toolkit review risk is UNKNOWN because size/traffic were not supplied. | Confirm production PostgreSQL version and ownership. Design a stable unique bigint-to-UUID mapping, UUID generation/default behavior, new unique keys, future FKs, writer compatibility and lock acquisition budget. Rehearse reviewed DDL elsewhere. | Keep all old fields and keys. Stop rollout before applications require incomplete new fields. |
| Backfill | `002_backfill_customer_uuid.sql:3-7` assigns customer UUIDs and copies them to children in three unbounded UPDATE statements. Toolkit review records zero operations/findings. Manual source review identifies missing bounded/resumable batching and concurrent-write coordination. | Define throttling and checkpoints. Coordinate all insert/update writers. Prove mapping uniqueness and completeness, no orphan child mappings and repeatable reconciliation under concurrent writes. Confirm `gen_random_uuid()` availability for the actual server. | Pause backfill and retain old data. An application reversal is safe only while both representations remain consistent. |
| Validate | Supplied files do not establish new UUID uniqueness, validated child FKs or application result equivalence. | Verify NULL rates, uniqueness, FK consistency and old/new results. Review supported NOT VALID/VALIDATE steps and concurrent index builds outside transaction blocks where appropriate. Inspect failed builds for invalid indexes. | Retain old constraints and data while fixing inconsistencies. |
| Transition | The view and both supplied application queries still read/join the old id representation. No deployment-completion evidence is supplied. | Transition readers, writers, FKs, view definitions, API parameter types and downstream jobs in an agreed order. Review UNKNOWN routine/default/identity dependencies. Observe old-field usage and errors through an agreed window. | Revert reads only if the retained representations remain consistent; otherwise use a reviewed roll-forward. |
| Contract | `003_contract_legacy_id.sql:3-4` changes the identity key by `id::text::uuid` and drops `orders.customer_id`. Toolkit risk is HIGH, with DDM001, DDM002, DDM008, DDM011, DDM014 and DDM015 findings. | Replace this proposal with a mapping-based design. Require validated new keys/FKs, transitioned views/apps, retained recovery data, tested backups and a separate destructive-change review. Review `addresses` as well as `orders`. | Reverse DDL cannot restore dropped data. Recovery depends on retained source data, tested backups or an operator's roll-forward procedure. |

Review artifacts are generated separately against the same unchanged baseline in `review-expand/`, `review-backfill/` and `review-contract/`. They do not prove the proposal files compose into a valid migration sequence. Lock duration, downtime, data correctness and lossless recovery have not been measured or verified.
